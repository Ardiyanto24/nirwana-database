## 2026-08-11 — Follow-up: investigasi + fix `guests_contact_view` lambat (Known Gap Checkpoint 3)
Did: Investigasi root cause `guests_contact_view` (2354ms, outlier dari 66 view lain 0.04-101ms, dicatat sebagai Known Gap "tidak diinvestigasi" di atas). Baca `plan_summary` yang SUDAH tersimpan di `monitoring.chatbot_explain_analyze_log` (id=9) alih-alih re-run query -- ketemu langsung: `Seq Scan` penuh pada `bookings` (217.654 baris, 1165ms) + `spa_bookings` (100.833 baris, 540ms) -> **external merge sort tumpah ke disk** (`Disk: 8136kB`) untuk `ORDER BY guest_id, activity_date DESC` demi `DISTINCT ON` -> 2127ms dari 2354ms (90%). Plus `Seq Scan` + sort disk terpisah (`Disk: 1664kB`) di sisi `guests` (24.893 baris) untuk `Merge Left Join`-nya, +224ms. Dikonfirmasi silang M3.3 (`mart_cleaned_indexes.py`): domain "guests" memang tidak pernah masuk 6 checkpoint M3.3 (tidak ada Filter Wajib role Data Analyst manapun yang menyentuh `guests`/`bookings.guest_id`/`spa_bookings`) -- gap nyata, bukan pengecualian disengaja.

**Temuan tambahan di luar dugaan awal**: `guests_profile_view` (M4.2, pasangan PII/profile split) ternyata punya subquery turunan `lap` yang identik byte-per-byte dengan `guests_contact_view` -- query langsung ke `chatbot_query_perf_snapshot` mengonfirmasi `guests_profile_view` JUGA lambat (473ms EXPLAIN, sampai 417ms `pg_stat_statements` bentuk terfilter), bukan cuma `guests_contact_view` seperti kelihatannya di data checkpoint 3 -- kemungkinan besar `guests_profile_view` waktu itu diuntungkan cache hangat karena dieksekusi ~0.7 detik setelah `guests_contact_view` dalam 1 sesi `explain_representative_queries.py` yang sama.

Fix dicoba bertahap (3 percobaan, 2 gagal terbukti empiris -- dicatat jujur, bukan disembunyikan):
1. **`idx_guests_guest_id` pada `guests(guest_id)`** -- **BERHASIL**. Menghilangkan `Seq Scan`+sort-disk di sisi `guests`, planner pindah ke `Index Scan`. Konsisten di setiap run.
2. **`idx_bookings_guest_bookingdate`/`idx_spa_bookings_guest_bookingdate` pada `(guest_id, booking_date)` ascending** -- **GAGAL, tidak kepakai planner sama sekali**, dites lewat `SET enable_seqscan=off` (planner tetap balik ke Seq Scan, membuktikan bukan pilihan cost-based).
3. **Recreate dengan arah yang cocok persis `(guest_id, booking_date DESC)`** (butuh extend `reindex_analyze.py`'s `_quote_column` sementara untuk dukung suffix DESC, di-revert lagi setelah terbukti tidak perlu) -- **TETAP GAGAL**. Dites `enable_seqscan=off` pada subquery `lap` terisolasi: planner MEMANG memakai index kali ini (`Bitmap Heap Scan`/`Index Scan`) tapi TETAP full-sort ulang sesudahnya (`Sort Method: external merge Disk`) -- plan hasil paksa ini malah 3x LEBIH LAMBAT (1465ms) dari plan alami (Seq Scan). Kesimpulan: PostgreSQL 17.6 tidak bisa membangun Merge Append untuk bentuk query `UNION ALL` + `DISTINCT ON` lintas subquery derived seperti ini -- keterbatasan planner struktural, bukan soal index yang salah. Kedua index arah-DESC ini DIBUANG lagi (drop) karena melanggar Keputusan #2 M3.3 sendiri ("hanya index yang empirically confirmed dipakai planner").

Sempat dicoba juga `work_mem` session lebih besar (32MB) sebagai eksperimen diagnostik terpisah (BUKAN diterapkan permanen, di luar scope index) -- `Sort Method` berubah jadi `quicksort` in-memory tapi cuma ~15% lebih cepat (422ms vs 502ms saat itu), tidak signifikan dibanding total biaya, dan mengubah konfigurasi role/session bukan "index" sesuai scope task -- tidak dilanjutkan.

**Temuan penting soal cache**: pembacaan awal setelah `CREATE INDEX`/`ANALYZE` menunjukkan `guests_contact_view` turun ke ~475ms (kelihatan seperti perbaikan 5x) -- ternyata SEBAGIAN BESAR itu efek cache Postgres/OS yang baru dipanaskan oleh proses `CREATE INDEX`/`ANALYZE` itu sendiri. Re-test setelah jeda menunjukkan angka **cold-cache kembali ke ~2801ms** -- nyaris sama dengan baseline 2354ms. Sistem ini memang tidak ada traffic produksi berkelanjutan (`chatbot_api` manual-only, dicatat sendiri di Known Gaps M6.5 di atas), jadi cold-cache lebih representatif dari kondisi nyata dibanding warm-cache. Run terakhir (dicatat ke `chatbot_explain_analyze_log` via `explain_representative_queries.py`) menunjukkan kondisi menengah: 492.1ms (`guests_contact_view`), 452.0ms (`guests_profile_view`).

Result: **Partial fix, root cause sisanya didokumentasikan sebagai limitation, bukan diperbaiki lebih lanjut** (keputusan eksplisit user, ditanya lewat AskUserQuestion setelah temuan planner limitation di atas). `idx_guests_guest_id` adalah perbaikan nyata & permanen (konsisten di semua run, menghilangkan 1 dari 2 sumber sort-ke-disk). Sisa ~85-90% biaya (`Seq Scan` + `external merge sort Disk: 8136kB` pada gabungan `bookings`+`spa_bookings`, ~318K baris) TIDAK bisa dituntaskan lewat index apapun -- dikonfirmasi empiris lewat `enable_seqscan=off` di percobaan #3 di atas. Ini murni karena view perlu menghitung "booking terakhir lintas SEMUA tamu" dalam 1 query tanpa filter selektif (semua ~318K baris di `bookings ∪ spa_bookings` memang harus disentuh), dikombinasikan keterbatasan PostgreSQL membangun Merge Append untuk bentuk `UNION ALL`+`DISTINCT ON` bersarang macam ini. Fix sungguhan (bukan index) akan butuh tabel ringkasan pre-computed (1 baris/guest, di-refresh tiap reverse-ETL sync) yang mengubah JOIN target view -- di luar scope "pure performance fix (index)" yang disepakati task ini, perlu keputusan arsitektur terpisah kalau mau dituntaskan (lihat Handoff Notes `report.md`).
