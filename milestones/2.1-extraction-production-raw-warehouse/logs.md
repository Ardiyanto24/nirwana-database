## 2026-08-08 -- Partitioning (Task 6) -- GAGAL, insiden kehilangan data, di-revert
Did: Tulis `scripts/extract/partition_tables.py` untuk 11 tabel yang punya kolom DATE/TIMESTAMP asli (dicek tipe via `bq show --schema`, bukan diasumsikan -- kolom text tanggal kotor seperti `employees.hire_date` sengaja dilewati). Pola: `CREATE OR REPLACE TABLE tmp PARTITION BY <kolom>` gagal duluan (tidak bisa ganti partitioning spec tabel existing via `CREATE OR REPLACE`) -- diperbaiki jadi pola create-tmp -> drop-original -> rename-tmp. Jalankan untuk 11 tabel, semua job "SUCCESS" menurut BigQuery.
Result: **BENCANA SENYAP** -- job sukses tapi row count anjlok drastis di SEMUA 11 tabel begitu dicek ulang (`bookings` 217.654 -> 1.958, `staff_shifts` 610.019 -> 12.968, dst). Investigasi lewat `bq ls -j` + `bq show -j` per job: `totalBytesProcessed` job CTAS-nya sendiri terbukti benar (memproses byte setara jumlah baris penuh) -- jadi data HILANG SETELAH CTAS berhasil, bukan CTAS-nya yang salah ambil data. Root cause ditemukan: dataset Sandbox mode punya `defaultPartitionExpirationMs`=60 hari (wajib ada, tidak bisa di-nol-kan -- `bq update --default_partition_expiration=0` ditolak eksplisit oleh GCP). Untuk tabel partisi berbasis KOLOM TANGGAL BISNIS (bukan waktu ingest), BigQuery menghitung kedaluwarsa tiap partisi dari NILAI tanggal partisi itu sendiri -- karena data production di sini historis (banyak baris bertanggal jauh >60 hari dari hari ini secara real-world), partisi-partisi itu otomatis dianggap kedaluwarsa dan terhapus nyaris seketika setelah dibuat.
Recovery: drop 11 tabel rusak (`bq rm -f -t`, sempat timeout di command loop pertama, lanjut manual untuk 3 tabel sisa), reset cursor state 11 tabel (`DELETE FROM monitoring.extract_cursor`), re-sync penuh dari Postgres (sumber tidak pernah tersentuh, jadi data asli 100% masih ada) -- validasi ulang 23/23 row count OK.
Keputusan akhir: Task 6 **dihentikan**, tidak dicoba ulang dengan workaround (ingestion-time partitioning dipertimbangkan tapi ditolak -- tidak memenuhi maksud asli "partisi sesuai kolom tanggal relevan"). Dicatat sebagai gap eksplisit, revisit begitu billing GCP aktif (script `partition_tables.py` sudah terbukti benar secara mekanis, cukup dijalankan ulang nanti).
Pelajaran: kalau ragu soal efek samping DDL yang belum pernah dicoba di lingkungan tertentu (Sandbox mode di sini), **verifikasi row count SEGERA setelah operasi**, bukan asumsi "job SUCCESS" = "data benar" -- BigQuery job status tidak mencerminkan kebijakan expirasi yang berjalan di background setelahnya.
