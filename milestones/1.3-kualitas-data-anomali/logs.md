## 2026-08-07 — Bangun 23 expectation suite dari rules_config.py (Task 3)
Did: Tulis `scripts/dq/rules_config.py` (27 rule dari katalog M1.1 + not_null/unique/accepted_values dasar untuk seluruh 23 tabel, termasuk 4 tabel prioritas Rendah sesuai keputusan cakupan penuh). Tulis `scripts/dq/build_and_run.py` (bangun suite via GE Fluent API + `UnexpectedRowsExpectation` untuk custom SQL rule).
Result: worked, dengan 1 bug syntax + 2 bug logika business rule ditemukan & diperbaiki saat run pertama kali (bukti nyata kenapa milestone ini perlu dijalankan dulu terhadap data live, bukan cuma ditulis di atas kertas):

1. **Bug syntax (ditemukan run pertama, semua 5 custom rule gagal)**: placeholder `{batch}` GE sudah tersubstitusi jadi `(...) AS subselect` — menambah alias sendiri (`AS t`) menghasilkan double-alias syntax error. **Fix**: hapus alias tambahan, predikat yang perlu merujuk balik ke baris batch (query dengan subquery ke tabel lain/tabel sendiri) pakai prefix `subselect.` bukan `t.`.

2. **Bug logika `staff_shifts` (112.502 lalu 31.044 false-positive, 2 iterasi)**: rule "clock_out > clock_in" ditulis dengan asumsi kolom bertipe timestamp. Ternyata `clock_in`/`clock_out` bertipe Postgres `time` (tanpa tanggal). Percobaan 1 (exclude shift Night) masih gagal 31.044 baris shift Afternoon — sampling data menunjukkan itu lembur sah yang berlanjut lewat tengah malam (clock_in ~15:00, clock_out ~00:xx-02:xx). **Fix final**: rule ini **dihapus total** dari suite — divalidasi lewat sampling bahwa keterbatasannya fundamental (kolom `time` tanpa tanggal tidak bisa membedakan "durasi negatif salah" dari "shift lewat tengah malam yang sah"), bukan sesuatu yang bisa diperbaiki dengan heuristik SQL tambahan. Dicatat sebagai keterbatasan skema nyata, bukan disembunyikan.

3. **Bug logika `financial_summary` (576 lalu 36 false-positive, 2 iterasi)**: rule awal (`gop`/`undistributed_expense` harus NULL kecuali baris `Overall`) salah asumsi NULL vs 0 — implementasi live memakai 0 sebagai sentinel "tidak berlaku", bukan NULL (576 false-positive). Setelah dikoreksi ke cek `!= 0`, tersisa 36 baris gagal — semua ternyata department `Corporate Overhead` (P06, kantor pusat), yang menurut `Metadata.md` "hanya biaya, tanpa revenue" dan memang konsisten (36/36 baris, diverifikasi via `COUNT`) punya `gop` terisi (P&L kantor pusat sendiri, bukan baris ringkasan seperti `Overall`). **Fix final**: kecualikan `Corporate Overhead` juga dari rule.

**Hasil akhir setelah semua fix**: 173/174 expectation lolos di 23 tabel. 1 kegagalan tersisa (`bookings.total_amount_matches_rate_x_nights`, 165/217.654 baris) adalah temuan production nyata (lihat entri sebelumnya), bukan bug rule.
